# Security model

Security is the first priority of HyScribe, above compatibility, performance and features. [VISION.md](VISION.md) explains why: the PHP runtime, the unsandboxed plugin model and agent-driven exploitation are the reasons HyScribe exists. A HyScribe that is merely as secure as WordPress has failed.

## Priority order

When goals conflict, decide in this order:

1. **Security** of the site, its users and its data
2. **Data compatibility**: the database and files stay valid for PHP WordPress
3. **Behaviour compatibility**: URLs, output, APIs
4. **Performance**
5. **Convenience and features**

Data compatibility is never traded away, because it is what makes switching back safe. Behaviour compatibility can be: a WordPress behaviour that is a known attack vector is off by default and can be enabled explicitly.

## Principles

- **Remove bug classes, don't just patch bugs.** Prefer designs that make a class of vulnerability impossible (memory safety, typed queries, no code execution from disk) over mitigations
- **Deny by default.** Extensions, endpoints, outbound network, file access: nothing is allowed unless declared and granted
- **Outbound fetches from core** (ADR 0019): none unless `HTTP_OUTBOUND=on`; HTTP and HTTPS only; connect and total timeouts and a response size limit; never to loopback, private, link-local or other non-public addresses, checked on the resolved address of every connection and redirect. With it on, the client fetches from any public address: it has no host allowlist. The RSS block's allowlist of hosts, which starts empty (2026-11-10), the embeds' allowlist, which starts as WordPress's oEmbed providers (`EMBED_ALLOWED_HOSTS`), and the opt-in for the dashboard's wordpress.org calls are separate, each on top of `HTTP_OUTBOUND`, and not built yet. Every redirect an embed or an RSS fetch follows must also lead to an allowed host (2026-11-19, a deliberate difference from PHP): otherwise the fetch stops, the embed stays a plain link or the feed shows the unreachable error, and nothing is cached
- **Never bug-compatible on security.** Ports reproduce a plugin's features, never its vulnerabilities
- **Small attack surface.** No PHP, no interpreter, no writable code directories, few dependencies
- **Secure defaults, explicit opt-in.** Defaults must be safe for someone who never reads the docs
- **Verify everything we ship.** Signed releases, reproducible builds, audited dependencies

## Threat model

| Actor | Goal | Main defenses |
| --- | --- | --- |
| Unauthenticated internet attacker | Code execution, data theft, defacement | Memory-safe core, no code execution from disk, typed queries, strict input parsing, rate limits, legacy endpoints off |
| Automated and AI-driven scanners | Mass exploitation within hours of disclosure | Bug class removal, fast signed updates, minimal surface, nothing exploitable in default config |
| Malicious or vulnerable extension | Escape to the host, read other data | WebAssembly sandbox, declared capabilities, resource limits, signed packages, registry review |
| Compromised low-privilege user | Privilege escalation | WordPress capability model enforced server side on every action, audit log |
| Stranger reaching a fresh install | Claim the site during setup | One-time wizard secret, setup mode timeout |
| Supply chain attacker | Poisoned dependency or release | `cargo-deny`, `cargo-audit`, `cargo-vet`, locked dependencies, reproducible builds, signed artifacts and provenance |
| Local user on the server | Read secrets | `.env` permission checks, refusal to run as root, no secrets in logs |

A threat model update is part of each milestone's exit (see [ROADMAP.md](ROADMAP.md)).

### Security review of the writes (MVP 9.2, 2026-11-18)

Every write on `development` at `f522d449` was read against PHP WordPress 7.1.3: hs-admin's actions and page view writes, `admin-ajax.php`, the REST writes, front end comments, login, logout, lost and reset password, and the upload helpers. Each was checked for capability checks made as PHP makes them, nonces and CSRF, hooks that could skip a check, SQL built only from bound values, output escaping, size and time bounds, open redirects, path traversal, header injection and shadow mode writing nothing. | S-13 | Info | Uploads | `wp_check_filetype_and_ext()` builds `proper_filename` from the name as given, path steps and all, as PHP does before its caller sanitizes it | Accepted: no handler uses a name before `sanitize_file_name()` inside `wp_unique_filename()`, a form's file name is its base name as in PHP, and the write takes a plain name only, in a folder resolved under the uploads folder. Each upload route (async-upload, Add New Media, `wp/v2/media` as a form and as a body) is tested against PHP with names that step out of the folder, absolute and backslashed paths, a NUL, a leading dot, only dots, a device name and a name over 255 bytes: the file, `_wp_attached_file`, the GUID and the title are PHP's, and nothing is written outside the uploads folder. The one difference these found is fixed: a NUL ends a form part's header line, as it ends PHP's |
| S-14 | Low | Uploads | A name that is not UTF-8 was sanitized to a name PHP never makes; a name ending in a line feed is no type to the ported check, where PHP's `$` takes it | Accepted: names that are not UTF-8 now sanitize as in PHP (the helpers' golden, and each upload route against PHP). Two differences stay, both the stricter way: no route can carry a line feed at the end of a name (a form's header line ends at it, as PHP's does, and a header holds none), and a file sent to `wp/v2/media` as a form under a name that is not UTF-8 is refused with nothing stored, where PHP stores the file, fails to insert its attachment and leaves the file (docs/COMPATIBILITY.md) |
| S-15 | Info | REST, redirects | A header the answer could not carry turned the whole REST answer into an empty 200, after a committed write too; the names of a collection's query parameters reach its pagination `Link` header unencoded, as in PHP, so a request could empty its own answer (never add a header: such a value is refused whole). The same class in the front end: a canonical or feed redirect could go out without its `Location` | Fixed: a REST header's whitespace collapses to single spaces as `send_header()` collapses it, and a header HTTP still cannot carry is left out alone, the status, the other headers and the body kept (PHP under Apache answers 500 there); canonical and feed redirects are sent through `wp_sanitize_redirect()`, as `wp_redirect()` sends them. Every other header set from a value that is not constant was read for the same pattern |
| S-16 | Info | Login | A relative `redirect_to` resolves from the root on a site in a subfolder (no host change); an administrator due to confirm the admin email lands on a 501 | Open: not security |

Where HyScribe matches PHP and keeps it (ADR 0003): the post-nonce redirects to `wp_http_referer` and `referredby`; a comment's editor moving it to another post or user; CORS answering any `Origin` with credentials; control characters and bidi overrides kept in upload names; `sanitize_file_name()` leaving `x.php56.jpg` as it is, since PHP underscores only a middle part of two to five letters and at most one digit. HyScribe is stricter than PHP where it costs nothing: user descriptions are always filtered, a REST `roles` change also needs `promote_user`, a bulk action refused part way writes nothing.

## Controls

### Code

- Rust everywhere; `#![forbid(unsafe_code)]` in every crate except a short, reviewed allowlist (for example, the WebAssembly host), each `unsafe` block justified in a comment and reviewed
- SQL only through the query layer with bound parameters; building SQL from strings is banned by lint and review
- Typed query arguments (`author__not_in` is a list of integers, not a string)
- PHP serialized data parsed as data only: serialized objects are kept as opaque values and never instantiated
- Templates auto-escape output by default; raw output needs an explicit, reviewed marker
- HTML sanitization (kses equivalent) for user content, per role
- No execution of any file from disk; only embedded code and signed extension packages run

### Web

- CSRF protection on every state-changing request (WordPress-compatible nonces)
- Security headers by default: `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `frame-ancestors`, HSTS when served over HTTPS. Embed pages, made to be framed by other sites, go without `frame-ancestors`
- Cookies `HttpOnly`, `SameSite`, and `Secure` over HTTPS
- Login rate limiting and lockout, built in rather than a plugin (see "Login rate limits" below)
- Two-factor authentication (TOTP and WebAuthn) built in, stored in HyScribe-owned usermeta keys that PHP WordPress ignores
- Off by default, opt-in for compatibility: XML-RPC, pingbacks and trackbacks, user enumeration via `?author=N` and the users sitemap. Author archives (`?author=N`, `?author_name=`, `/author/<nicename>/`) turn on with `AUTHOR_ARCHIVES=on` (decision 2026-11-25), which serves them as WordPress does, the `?author=N` redirect to the author's nicename included. The other opt-in keys are planned, not built (XML-RPC with M9); the users sitemap stays off
- On by default, as WordPress serves it: the public users REST endpoint, which lists every user with published posts to visitors; the owner turns it off with `REST_PUBLIC_USERS=off` in `.env`, which answers visitors as a site where no user has published posts. Login rate limiting and lockout limit what an attacker can do with the names it shows
- Safer by default: the capability constants are `.env` keys the setup wizard copies from `wp-config.php`, and a missing key takes the safer value. `DISALLOW_UNFILTERED_HTML` is true, so no one, administrators included, may post unfiltered HTML until the owner sets it to false; `ALLOW_UNFILTERED_UPLOADS` is false; `MULTISITE=true` is refused at start. A value other than the yes or no words every such key takes (true, yes, on, 1, false, no, off, 0) stops the start rather than being guessed. The values are read once into the site's configuration, which every capability check reads. As in PHP, only a user whose check grants `unfiltered_html` saves posts' titles, content and excerpts (and comments) without kses and sees `htm`, `html` and `js` among the uploader's allowed types; term descriptions, user fields and options are filtered for everyone
- A global styles value containing `{` or `}` is dropped as an unsafe value is (2026-11-19, a deliberate difference from PHP), in `remove_insecure_properties()` and in the stylesheet's own check, so `red;} body{x:y}` cannot end one declaration and start a rule; PHP's `safecss_filter_attr()` splits such a value at its `;` and keeps the first part. Every other value is filtered exactly as PHP filters it, and no PHP golden has a brace in a value except the `insecure` case with the font family `Arial; } body{x:y`, whose expected answer drops it
- A trackback GET redirects to its post's link only for a published post or page; WordPress links any post ID, which tells drafts, private posts and templates apart from IDs with nothing
- A trackback POST is answered that trackbacks are closed, for every post, and nothing is stored

### Login rate limits

PHP WordPress has none: every guess at `wp-login.php` costs a bcrypt check at cost 12, so unlimited guessing is both brute force and CPU exhaustion. HyScribe adds limits to `/hs-login`, a deliberate difference from PHP (ADR 0018). It is the only path that checks a user's password: REST cookie auth checks a cookie, application passwords and XML-RPC are not served.

- Counted per client address and per account. The address is the connection's, or under `BEHIND_PROXY`, from a peer in `TRUSTED_PROXIES`, the last entry of all the request's `X-Forwarded-For` lines read in order as one list, which is the one the trusted proxy appended, as `ip`, `ip:port`, `[ipv6]` or `[ipv6]:port`; an IPv6 address by its /64. Where that entry names no address (`unknown`, garbage), the limits step of `authenticate` gives the guess no turn, so it fails for that request alone without being checked or counted, and is logged; it is never counted under the proxy's own address, which every client shares. A guess is a login with a non-empty password; it fails when no password it was checked against matched, an unknown account included, and is counted from `wp_login_failed`, as login limiting plugins count, which does not fire for a blank username
- An address with `LOGIN_LIMIT_ADDRESS` failures (default 5) within `LOGIN_LIMIT_WINDOW` seconds (default 900) is refused for the window, doubled for each refusal of the day before, up to a day: about 40 guesses a day from one address at the defaults
- An account with `LOGIN_LIMIT_ACCOUNT` failures (default 10) in the window, from any addresses, is refused for the window, never longer, against attackers spread over many addresses. It is not refused from the last 8 addresses it logged in from since the start, so an attacker cannot lock its owner out where they usually log in, nor push them out with logins of their own account
- One address checks one password at a time: a guess that arrives while another request of its address is being checked is answered as wrong and counted, so guesses sent at once cannot slip past the count
- Site wide, at most as many password checks run at once as the machine has CPUs. A check over the cap waits up to 2 seconds in a line of at most 8 per CPU; past the wait, or with the line full, the guess is answered as a wrong password without its hash checked, and is not counted, so a flood does not refuse the addresses of real users caught in it
- The limits run as the `hyscribe_login_limits` callback of the `authenticate` filter at priority 10, ahead of core's password checks at 20: it gives a guess its address's turn, and no password is checked without one. Core's `wp_authenticate_cookie` (30) and `wp_authenticate_spam_check` (99) keep their priorities; a later extension can add callbacks or replace one by name, and the account limits and the site wide cap stay in the password check itself
- A refused guess is answered exactly as a wrong password, before its hash is checked: the right password fails too, and an unknown account answers as unknown, as PHP does, so nothing tells a refusal or an account's existence apart from PHP's own answers. Guesses while refused are not counted, so they do not lengthen a refusal; a successful login does not reset its address's count, so a registered account cannot be used to clear it
- State lives in memory only, never in the database (ADR 0003), and is lost on restart. Each of the address, account and trusted login maps holds at most 65,536 entries; a full map first drops entries whose window and day are over, then the sixteenth least recently active (a refusal counts as active until it ends, so a flood of new addresses drops itself before a refused one), so the sweep is paid once in thousands of new entries
- The defaults let a user mistype a few times and an attacker make few guesses; the account limit is twice the address limit so one address alone never refuses an account

### Uploads and media

- Uploaded files are never executed; served as static files with `nosniff` and a strict content type: images (but SVG), audio, video, PDFs and plain text are shown with their type, and any other file, HTML and SVG among them, is sent as an `attachment` download. A path that is not a plain file inside the uploads folder (`..`, a hidden name, a link leading out) is not found
- An upload is written under a temporary name, then linked to its own, so a crash leaves no half file, and never outside the uploads folder; its body is refused (413) as soon as it passes `UPLOAD_MAX_SIZE` and its form, with at most 16 upload bodies read at once, and a file over `UPLOAD_MAX_SIZE` is refused as PHP refuses one over `upload_max_filesize`. The multipart reader and the `Content-Disposition` reader are fuzzed (`multipart_form`)
- File type checked by content, not extension; executable and script types rejected
- SVG sanitized or served as an attachment download
- Image decoding with size and pixel limits to stop decompression bombs (ADR 0015, `hyscribe-image`): width, height, area and memory are checked from the header before a decoder starts, at the oracle's ImageMagick policy by default (32,000 a side, 256,000,000 pixels, 1 GiB, the memory counted as the source's bytes a pixel plus 36 for the editor's working copies, with checked arithmetic); each decoder then reads the size itself (JPEG's frame header, PNG's `IHDR`, GIF's screen, WebP's header), which must pass the same limits and equal the header's before any pixel buffer is allocated, so two parsers that disagree (zune-jpeg skips `FF 00` as fill where PHP's marker walk does not) refuse the image; a GIF's first frame, which may be larger than its screen, is checked before its buffer is allocated; no file over 64 MiB is decoded. What a PNG decoder allocates itself, its metadata inflated (`iCCP`, `zTXt`, `iTXt`) and a row, has its own 16 MiB limit apart from the pixels' memory, and a profile over it is dropped; one job's memory is therefore its pixel budget plus at most 16 MiB of metadata and its copy. An image over a limit, or one its decoder rejects, is kept with the size its header gives and no sizes, as WordPress keeps an image its editor fails on
- Images are decoded and encoded only by pure Rust crates with SIMD off, each audited with cargo vet (`zune-jpeg`, `png`, `gif`, `image-webp`, `jpeg-encoder`, `kamadak-exif`); `hyscribe-image` forbids `unsafe`, nothing shells out, and AVIF, BMP and HEIC, which have no safe codec, are kept without sizes
- HyScribe's own parsers of uploaded bytes, the image header reader and the IPTC reader, are fuzzed (`image_header`, `image_iptc`), and so is the whole upload pipeline under small limits (`image_pipeline`), each seeded with the hostile cases in `crates/hyscribe-image/tests/hostile`; the IPTC reader runs in time linear in its datasets, and EXIF is read only within its `APP1` segment (at most 64 KiB), as PHP reads it; EXIF and XMP that PHP would read in ways not ported refuse the upload (501) rather than being guessed
- Only the first frame of an animation is decoded; sizes carry the source's ICC profile but no EXIF, IPTC or XMP (WordPress's Imagick editor keeps them), so a size never repeats a photo's location
- Resizing runs in a bounded worker pool sized to the CPUs, never on a request's thread; jobs beyond it wait in a bounded queue, so the memory in use stays the pool's size times one job's budget (pixels and metadata, as above). A job that panics, in a decoder or the resampler, ends only its own run: release builds unwind (`panic = "unwind"`, and `hyscribe-image` refuses to compile with `abort`), and the pool catches the panic; a stack overflow still aborts the process

### Extensions

- WebAssembly sandbox with no ambient access: database tables, options, files, outbound hosts and mail only as declared in the manifest
- CPU (epoch interruption) and memory limits per call: 50 ms a call, 250 ms an extension a request and 16 MiB an instance by default, more only as the manifest asks and the administrator approves, never past 500 ms, 2,000 ms and 64 MiB (ADR 0022); no WASI, no compiled code read from disk, one fresh instance per extension per request
- Every host call checks its grant in the store's state before it touches anything and answers `denied` otherwise (MVP 11.2); registrations (hooks, post types, taxonomies, meta, REST routes, shortcodes, blocks) are taken in `init` only, everything else in a request only; asset sources and blocks are paths inside the package, mail attachments paths under a granted `uploads/` folder, never with `..`, `\`, `:` or an empty step; a query reads public post types and granted ones only, and `any` is refused
- Security sensitive hooks (`authenticate`, `user_has_cap`, `map_meta_cap` and the others ADR 0022 lists) need a grant of their own, shown apart with a warning before activation; the host's list also holds the hooks that see passwords and reset keys (`retrieve_password_key`, `wp_set_password`, `password_reset`, `after_password_reset`) and the mail actions (`wp_mail_succeeded`, `wp_mail_failed`), and firing a sensitive hook from an extension needs the grant too; `phpmailer_init` is refused
- "A hook never skips a check" holds for extensions through the same grant (ADR 0022's 2026-11-25 amendment): the hooks that can answer a REST request before its checks or replace what they let through, that change a save or an upload after its checks, or whose answer decides a check are sensitive hooks, whatever values cross today; any other hook's answer goes through the checks the value it replaces goes through
- An extension's REST route (SDK 0.5, ADR 0022's 2026-11-27 amendment) is served through `hyscribe-rest`'s dispatcher after core's routes, which it can never shadow: the cookie and nonce check, `rest_pre_dispatch`, its arguments checked and sanitized by their schemas and its own callbacks, then its permission callback, whose answer allows only when it is `true`, and its callback only then; each within the per call and per request budgets, a fault answering PHP's critical error page; its namespace is granted and never core's, its route a regex of the bounded engine, at most 256 routes an extension; its answer's headers are limited to those an API answer needs (no cookie, framing, encoding, content type, CORS, nonce, security policy or server file headers), then collapsed and dropped as core's; the request it is given holds no cookie or credential; an extension is never entered twice, so a chain fired while it runs skips its own callbacks
- An extension's admin page (SDK 0.4) runs its callback only for a user with its capability, checked by the host as `user_can_access_admin_page()` does, and only when the callback is on the page's hook for that user, as `admin.php` checks (a top level page asked under another menu the user may reach answers "Cannot load"); its slug is letters, digits, `_` and `-` only, its icon a `dashicons-` class of the same, a setting it registers needs its option's grant, and `settings_fields()` prints only a group the extension registered
- 3 trap, timeout or memory faults within 10 minutes disable an extension until an administrator re-enables it; the state is kept in its folder (`faults.txt`), never in the database, and a record that does not read counts as disabled
- Packages signed; unsigned packages need an explicit operator override
- Admin shows requested capabilities before activation; capability increases on update need re-approval

### Secrets and process

- `.env` must be mode `0600`; the binary refuses to start otherwise
- The binary refuses to run as root (or drops privileges after binding ports)
- Windows is the exception to both (below)
- Secrets redacted in logs and error pages; no stack traces to visitors
- Setup mode requires the one-time secret and expires if setup is not completed

### Windows

Windows (ADR 0005's amendment of 2026-11-27) lacks what three of these protections stand on, and HyScribe keeps to safe Rust there too, so they are not matched; what replaces them is the operator's part, in docs/operators/install.md and security.md:

- **File modes.** Windows has no modes, and access lists cannot be set or read without `unsafe` code or a new dependency. `.env`, session files, `logs/setup-secret`, the logs, `run/` and kept packages take the access list of the folder they are in, and the refusal of an `.env` others can read does not run; Site Health reports that it could not check. Kept inside the account's profile folder, which Windows opens only to that user, administrators and the system, the files are as private as `0600` makes them; elsewhere the operator restricts the folder with `icacls`
- **Root.** An administrator (an elevated token) cannot be told without the token calls `unsafe` would need, so `effective_uid()` reports no root on Windows and nothing is refused: the documentation says to run HyScribe from an ordinary account
- **Signals.** `service stop` writes one byte to the server's named pipe `\\.\pipe\hyscribe-<pid>`, made before the server takes its lock with the first instance flag (a name another process holds is refused) and closed to remote clients. The pipe's default access list grants write only to the server's own user, administrators and the system; anyone else may connect and read, which asks for nothing, and a client that connects and writes nothing is dropped after a second. Only the pid the lock holder wrote is asked, as on Unix
- **Sockets.** A socket `DB_HOST` is refused: the database driver has no named pipes
- **Names.** Uploads and attachments whose names Windows would read as something else (devices such as `CON` and `NUL`, `:` streams, trailing dots and spaces) are refused there

## Porting and security

Agent-ported plugins are the largest new attack surface, so the porting pipeline ([PORTING.md](PORTING.md)) adds security gates:

- The analyzer looks up the original plugin's published vulnerabilities, and the port must include regression tests proving none of them are reproduced
- Ports request the smallest capability set that passes the differential tests
- Generated code follows the same rules as core: no `unsafe`, no string-built SQL, auto-escaped templates
- Differential tests include attack payloads, where the expected result is that HyScribe blocks the attack even if the PHP original did not

## Release blockers

A release cannot ship with:

- Any open critical or high severity finding
- Any `unsafe` code outside the reviewed allowlist
- Any dependency with a known unpatched advisory, unless documented as not reachable
- A parser without a fuzz target
- Coverage below 100% or surviving mutants in security-critical crates ([ADR 0007](adr/0007-full-test-coverage.md))
