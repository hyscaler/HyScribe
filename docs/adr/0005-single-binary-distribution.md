# 0005: Single binary distribution

- Status: Accepted
- Date: 2026-10-26

## Context

WordPress is installed by extracting `latest.tar.gz` and opening a browser. HyScribe should be at least that simple, without requiring a web server, PHP, or Docker. A single self-contained binary that runs itself as a service and sets itself up through a browser or terminal wizard gives operators that.

## Decision

- The primary distribution is a per-platform archive (`hyscribe_<version>_<os>_<arch>.tar.gz` plus a `hyscribe-latest-*` alias) containing one statically linked binary, `LICENSE` and `README.txt`
- Everything needed at runtime is embedded in the binary: admin UI, `wp-includes` assets, a default theme, the extension runtime
- The binary manages itself as a background service (`service start|status|log|restart|stop`) with its pidfile in `run/` and logs in `logs/`
- First start without configuration boots setup mode: browser wizard protected by a one-time secret (default) or terminal wizard
- Configuration lives in `.env` next to the binary; real environment variables override it
- The `hyscribe/` folder holds the whole installation in plainly named folders: `plugins/<slug>`, `themes/<slug>`, `languages/`, `uploads/` (new sites), `packages/`, `reports/`, `cache/`, `logs/`, `run/`. Only an existing site's media library stays in its original `wp-content/uploads`
- WordPress URL paths (`/wp-content/...`) are preserved and mapped onto these folders
- Docker images are an optional, secondary distribution of the same binary

## Consequences

- Install, upgrade and removal are file operations on one folder
- Binary size grows with embedded assets; acceptable, but tracked (risk R13)
- `wp-includes` assets are bundled, which settles where `wp-includes` assets come from
- The configuration format changes from the earlier `hyscribe.toml` draft to `.env`
- Boot autostart and self-update are not covered yet

## Amendment (2026-11-26): macOS archives

- macOS joins Linux as a release platform: `hyscribe_<version>_darwin_arm64.tar.gz` (Apple Silicon) and `hyscribe_<version>_darwin_amd64.tar.gz` (Intel), each with its `hyscribe-latest-darwin-<arch>.tar.gz` alias, holding the same files as the Linux archives. The deliverable stays the plain binary in a `tar.gz`: no `.dmg`, no `.pkg`, no app bundle
- They are built on macOS, on a GitHub-hosted runner, and never cross-compiled from Linux: the build then uses Apple's own linker and SDK, on the system the binary is for, where it can be started and tested. The Linux archives stay on the project's self-hosted runners
- "Statically linked" cannot hold on macOS, which has no stable system call interface and no static C library: the binary links the system's own libraries and nothing else. The rule that matters is kept, no runtime dependency to install other than the database
- The build targets macOS 11.0, the first release for Apple Silicon, for both architectures (`MACOSX_DEPLOYMENT_TARGET` in `scripts/package.sh`)
- Each archive is smoke-tested on the runner before it is uploaded: installed, started against the default install fixture in a MariaDB installed on the runner (`reference/default-install/db-native.sh`, since the runner has no Docker), a page fetched, stopped. The Intel binary runs under Rosetta, since the runner is an Apple Silicon machine
- Each archive is built twice on the runner and the bytes compared, as for Linux, and they are the same. The Linux builds take their compiler and C toolchain from one pinned image; the macOS bytes also depend on the runner image's Xcode, SDK and Homebrew tools (GNU tar), which only the image's label (`macos-15`) pins, so a later image may give other bytes for the same commit
- The binaries are not signed with an Apple Developer ID or notarised. Until they are, a copy downloaded with a browser has to be allowed by its user (docs/DEPLOYMENT.md, "macOS"). Checked on the macOS 15 runner: a file fetched with `curl` carries no quarantine mark, `tar` copies an archive's mark to what it unpacks, `spctl` rejects the binary, and `xattr -d com.apple.quarantine` removes the mark; the refusal to start is macOS's documented behaviour and could not be shown on the runner, where a marked binary still ran from the job's shell. Signing needs an Apple developer account and its certificate in the release workflow, a decision still open
- The certificate store on macOS is the bundle the system ships (`/etc/ssl/cert.pem`), read by the same code as on Linux, not the Keychain: reading the Keychain would need the Security framework through FFI, which ADR 0019 avoided
- Boot autostart stays out of scope here too (a launchd job on macOS)

## Amendment (2026-11-27): the container image

- The container image named in the decision is built: `docker.io/hyscribe/hyscribe` on Docker Hub and `ghcr.io/hyscaler/hyscribe` on GitHub Container Registry, the same digests on both, for `linux/amd64` and `linux/arm64`, tagged `<version>`, `<major>.<minor>` and `latest` (a pre-release only by its version). It stays optional and secondary: the archives are the primary distribution, the docs lead with them, and no feature depends on Docker
- **Built per published release, from its archives on GitHub, never compiled in Docker** (2026-11-27), for both amd64 and arm64, on Debian slim. Publishing a release starts the workflow `docker.yml`, so no image goes out before its release. It verifies each Linux archive's build attestation (signed by the release workflow, for that tag) and its line in the release's `SHA256SUMS.txt`, and passes each SHA-256 to the Dockerfile, whose `ADD --checksum` downloads the archive from the release again and fails on any other bytes. The binary that was built, tested, smoke-tested and attested as an archive is copied into the image unchanged, so the image cannot hold a different build, and anyone can rebuild a release's image from the Dockerfile and those arguments. Every `RUN` runs on the build platform (unpacking, Debian's CA bundle) and the target's stage only copies, so the arm64 image needs no emulation on the amd64 runners. A manual run builds the image of an existing release and checks it, and pushes only when asked
- **Base:** Debian's `debian:trixie-slim`, pinned by its multi-architecture index digest, with Debian's `ca-certificates` bundle (and its copyright file) and a `nonroot` user, uid and gid 65532, added: the same uid as the distroless base the first image used, so volumes made by that image keep working. The binary reads the CA certificates from the filesystem for outbound HTTPS and the mail relay. Debian slim brings a shell and the usual tools, for looking inside a running container, at the cost of a larger image and more packages to keep updated than distroless; the server's own refusal of root holds in the container too
- **`HYSCRIBE_HOME`:** the installation's folder was always the binary's own. A container must keep its data on a volume while the binary comes from the image, or an old binary in a volume would outlive every upgrade; so the environment variable `HYSCRIBE_HOME`, an absolute path to an existing folder, now names the installation's folder instead, and the image sets it to its volume `/hyscribe`. Unset, nothing changes for an archive install. It is read from the environment only, never from `.env`, which lives in that folder. v0.1.0's binary predates it, so the first release with an image is the one after v0.1.0: the check job's smoke test refuses v0.1.0's image, whose binary tries to write beside itself
- **Configuration and logs:** environment variables win over `.env` as before, so a container is configured by `-e` or by the wizard's `.env` in the volume. `hyscribe start` runs in the foreground and logs to standard output, for `docker logs`; `service start` and its log file are not used in a container, and Docker's restart policy replaces starting at boot
- **Reproducible while Debian's `ca-certificates` stays the same:** the bases and the Dockerfile frontend are pinned by digest, timestamps come from the release's commit (`SOURCE_DATE_EPOCH`, `rewrite-timestamp`) and there is no BuildKit provenance, which records the build's time. The check job builds the image twice, the second time without cache, and compares the digests; the push job builds it again and pushes only that digest. The CA bundle is Debian's package of the day, so a rebuild after a Debian update of it gives another digest with the same binary. Its provenance is the workflow's attestation (`actions/attest-build-provenance` with `push-to-registry`)
- **Publishing:** when a release is published, or by hand with `push`, from the push job after the check job, with the job's own `GITHUB_TOKEN` for GitHub Container Registry (`packages: write` on that job only) and the repository secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` for Docker Hub, which receives a copy of the pushed manifest (`docker buildx imagetools create`), not a second build. The check job logs in to Docker Hub on every run, so a wrong token shows before a release needs it; without the secrets the Docker Hub steps are skipped with a notice. `latest` goes with a release only while it is GitHub's latest release, so rebuilding an older one leaves it. No third-party actions: the logins and pushes are `run` steps
- **Tested** on the self-hosted Linux runners by the check job, before any push: each platform's `/usr/local/bin/hyscribe` compared byte for byte with its archive's binary, and the amd64 image run by `scripts/docker-smoke-test.sh` as its user (65532) with a read only root filesystem and the data on a named volume, against the default install fixture, then as a new site through the browser wizard. The arm64 image is checked by contents only, as no arm64 machine or container emulation is available there. CI and the release workflow no longer build the image: it is made only from a published release
- **Not covered:** image signing beyond the attestation (for example cosign), images for other systems (Docker Desktop runs the Linux image on macOS and Windows), and `service start` inside a container

## Amendment (2026-11-27): Windows archive

- Windows joins as a release platform: `hyscribe_<version>_windows_amd64.zip` with its `hyscribe-latest-windows-amd64.zip` alias, holding the same files as the other archives, the binary being `hyscribe.exe`. No installer, no MSI. arm64 Windows is not built
- It is built on Windows, on a GitHub-hosted runner (`windows-2025`), with Visual Studio's compiler and linker, never cross-compiled; the Linux archives stay on the self-hosted runners. The C runtime is linked in (`+crt-static`), so the rule that matters holds: no runtime dependency to install other than the database. The zip is written by `scripts/package.sh` in Git for Windows's bash, through Python's `zipfile` with sorted entries dated at the commit, and smoke-tested on the runner against the default install fixture in MariaDB's own zip for Windows (`reference/default-install/db-native.sh`)
- Reproducibility: the build passes `/Brepro` to the linker, which puts a hash of the binary where it would write the build time, strips symbols so no PDB path is embedded, and remaps the checkout's paths; the zip carries no file times or attributes of the machine. The job rebuilds and compares the bytes; they depend on the runner image's Visual Studio and Windows SDK, which only the label pins
- The service stays the same design and the same commands, not a Windows service: `service start` runs the server as a detached process with its own process group and no console, holding the lock that decides "running". A Windows service would need the service control manager's API, administrator rights to install, and code outside the safe subset; a detached process needs none of them and keeps the pid file guarantees. Two things differ:
  - Windows locks refuse reads by other handles, so the lock is held on `run/hyscribe.lock` and the pid file beside it is read freely. A stale pid file is still never taken for a live server, since only the lock decides
  - Windows has no signals. The server makes a named pipe of its own, `\\.\pipe\hyscribe-<pid>`, before it takes the lock, and `service stop` writes one byte to it: a stop request, taken as SIGTERM (logged as `stopped on signal 15`), then after the grace period a kill request, on which a thread of its own ends the process at once, as SIGKILL. The pipe's default access list grants write to the server's own user, administrators and the system only, its first instance flag refuses a name another process holds, and remote clients are refused. A named event or `CTRL_BREAK_EVENT` would have needed `unsafe` calls (and, for console events, a shared console the detached server does not have); `TerminateProcess` on a pid not spawned by the caller needs `unsafe` too, and running `taskkill.exe` would execute a program from disk. Ctrl-C at a foreground `hyscribe start` counts as SIGINT
- What cannot be matched in safe Rust, and is documented instead (docs/SECURITY_MODEL.md, "Windows"; docs/operators/install.md): file modes (files take the folder's access list, the `.env` check does not run, and operators keep the folder in their profile or restrict it with `icacls`), the refusal of root (an administrator is not told apart), the free disk space on Site Health, and Windows's certificate store (only a PEM bundle named by `SSL_CERT_FILE`, as the probe reads it). A socket `DB_HOST` is refused, since the database driver has no named pipes
- Paths: the `hyscribe/` layout is the same; what is written to the database keeps `/` as PHP writes it; upload and attachment names Windows would read as devices (`CON`, `NUL`, `COM1`), streams (`:`) or trim (trailing dots and spaces) are refused; Rust's standard library takes long paths to the extended form. Every file is checked out as stored (`.gitattributes`: `* -text`), so templates, goldens and embedded files keep their LF line endings on Windows
- The binary is not signed with Authenticode. SmartScreen may stop the first start of a copy downloaded with a browser; the documentation says how to verify the download and allow it. Signing needs a code signing certificate in the release workflow, a decision still open
- CI's `windows` job runs clippy, a build and the tests of the crates that need neither the fixture database nor the Theme Test Data on the runner; the full suite runs on Linux only. The minimum is Rust's own for the target: Windows 10 and Windows Server 2016
