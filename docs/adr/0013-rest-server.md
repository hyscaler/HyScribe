# 0013: The REST server

- Status: Accepted (2026-11-16)
- Date: 2026-11-14

## Context

The block and site editors read and write through the REST API (docs/MVP.md, phase 4). WordPress serves it from `WP_REST_Server`: `rest_api_loaded()` takes any request whose `rest_route` query var is set (from `?rest_route=`, or from the `/wp-json/` rewrite rules under pretty permalinks), authenticates it, matches it against the registered routes, checks the route's arguments against their JSON schemas and calls the endpoint's permission check and callback. About 130 routes in 5 namespaces are registered on a default install, and each route answers in the `view`, `embed` and `edit` contexts differently for each role. The routes arrive over several work packages, and writes wait for phase 2.

## Decision

- **A crate, `hyscribe-rest`.** The server and its routes live in a crate of their own, pure and synchronous like `hyscribe-render` and `hyscribe-admin`: a request and the site's data go in, the status, headers and body come out. It is tested without a database, replays the PHP oracle's answers for every role, and has a fuzz target (`rest_serve`) over every input a request carries. `hyscribe-http` keeps what is about HTTP and sessions: finding the `rest_route` query var after the rewrite rules, reading the cookie, and sending the answer.
- **Routes from WordPress's own table.** The routes WordPress registers, with each endpoint's methods, are exported from the oracle (`reference/wordpress/export.sh`, `wordpress/wp-includes/rest-routes.json`) and matched as `match_request_to_handler()` matches them: the request's namespaces first, each route's regex as `@^route$@i` with the `preg_match()` engine the rewrite rules use (moved to `hyscribe-phpser`). A route is ported whole, every endpoint with its arguments, permission check and callback, registered in a `match` on its regex; so `rest_no_route`, and `Allow`, are exactly PHP's whatever is ported.
- **501 for what is not ported.** A request that matches a route not ported, the description (`OPTIONS`) of such a route, an argument whose schema uses a keyword not ported, or a `rest_route` or `_method` that is not a string is answered `501` with no body. Every write method (`POST`, `PUT`, `PATCH`, `DELETE`) answers `501` until phase 2: no write endpoint is ported, and a write that matches no route is PHP's `rest_no_route`.
- **Reads through a trait.** Routes read the site through `hyscribe_rest::Site` (options, `rest_url()`, the nonce, capabilities), which `hyscribe-http` implements over the existing read path (`LoginReads` and `Reads`, ADR 0009), on a blocking thread, with database errors shown as the error page. Data that is registration rather than content, such as the post types' labels and capabilities, is exported from the oracle beside the route table.
- **Cookie authentication over HyScribe's sessions.** The logged in cookie (`hyscribe_logged_in_*`, ADR 0011) is validated as `wp_validate_logged_in_cookie()` validates WordPress's, against HyScribe's sessions. As `rest_cookie_check_errors()` does, a request without a `wp_rest` nonce (`_wpnonce` in the form or query, or `X-WP-Nonce`) is a visitor's, a nonce that does not verify for the cookie's user answers `rest_cookie_invalid_nonce`, and a good one is refreshed in `X-WP-Nonce`. The nonce is `wp_create_nonce( 'wp_rest' )` with HyScribe's salts and the session's token, as hs-admin prints it. Application passwords and other authentication are not ported.
- **The index waits.** `/` and the namespace indexes list every route's arguments and schemas; they are served when every route they describe is ported and they can match PHP byte for byte, and answer `501` until then (the root index is amended below).

## Consequences

- Each later route is a module in `hyscribe-rest` with goldens from `reference/rest/golden.sh`; the server, its errors, `_fields`, `_envelope`, `_embed` (embeddable links served as internal requests; one to a route not ported leaves the whole request 501), `_jsonp`, `_pretty`, `context`, CORS, the pagination headers and schema validation are shared.
- Where PHP answers an unported route, HyScribe answers 501, which an editor shows as an error rather than as wrong data.
- The route table and post type data change with the pinned WordPress version and are re-exported with it.

## Descriptions from exported data (2026-11-16)

- A ported route's description (`OPTIONS`) is served as `rest_handle_options_request()` gives it: the first route the path matches, whatever its namespace or methods, described by `get_data_for_route()` in the `help` context. The descriptions of every route are registration data, exported by `reference/wordpress/export.sh` as `wordpress/wp-includes/rest-descriptions.json` with the REST URL as a placeholder; the `Allow` header runs each endpoint's permission check over the unchecked URL and query parameters, as PHP does. They match PHP for a visitor and each role (`reference/rest/preloads.list`).

## Amendment: the index from exported data (decided, 2026-11-16)

The block editor preloads the index (`/?_fields=description,gmt_offset,home,...`) for the site's settings, so its page cannot be served while the index answers 501. The same export could serve it: `get_index()` is the site's options, `home_url()`, the namespaces, `authentication`, the image settings for users who may upload, and the routes' descriptions in the `view` context (the exported ones without `schema`), with the `rest_index` filters' site logo and icon fields and links; a namespace index is its namespace's routes. Options:

- Serve the index whole from the export, every route described as PHP describes it, including routes HyScribe answers 501 (the index then advertises routes that are not ported)
- Serve the index, but answer 501 when `_fields` asks for `routes` or `namespaces` (or gives no `_fields`); the editor's preload, which asks only for site fields, is served
- Keep the decision above: 501 until every route is ported

The second option was chosen (2026-11-16): the index is served from the export, and answers 501 when `_fields` asks for `routes` or `namespaces` or gives no `_fields`.

Built (2026-11-16) in `hyscribe-rest`'s `index` module, as `get_index()` gives it:

- **Served:** the site's name, description, URL, `home_url()`, `gmt_offset` (through `wp_timezone_override_offset()`, a named zone's offset at the request's time), `timezone_string`, `page_for_posts`, `page_on_front`, `show_on_front` and `authentication`; for users who may upload, in a secure context (an https site URL, or a `Host` of `localhost` or a subdomain of it, as `wp_is_client_side_media_processing_enabled()` reads it), `image_sizes`, `image_size_threshold`, `image_strip_meta` and `image_max_bit_depth`; `site_logo` (the `site_logo` option, else the theme's `custom_logo` mod), `site_icon` and `site_icon_url`, each image with its `featuredmedia` link; and, when `_fields` asks for `_links` or `_embedded`, the `help` and `active-theme` links. The block editor's preload, `/?_fields=description,gmt_offset,home,image_max_bit_depth,image_sizes,image_size_threshold,image_strip_meta,name,site_icon,site_icon_url,site_logo,timezone_string,url,page_for_posts,page_on_front,show_on_front` in 7.1.3, is served.
- **501:** a request whose `_fields` keeps `routes` or `namespaces` as `rest_filter_response_fields()` reads it, or that gives none (an empty `_fields` too); on an https site, one that keeps `authentication`, where PHP lists application passwords, which are not ported. As the routes are never served, the export's `view` descriptions are not needed; the index's own description (`OPTIONS`) is served from the `help` export as any ported route's.
- **Namespace indexes:** each lists its namespace's routes, so it would be served only once every route of its namespace is ported. None is yet (`wp/v2` lacks the plugins, widgets, sidebars, fonts, icons and others; `oembed/1.0`, `wp-site-health/v1`, `wp-block-editor/v1` and `wp-abilities/v1` have no route ported), so every namespace index answers 501.
- **Oracle:** `reference/rest/index.list` on the default install, `index-site.list` (a site icon, a theme's logo, a named zone) and `index-logo.list` (the `site_logo` option, a post and a page as images), for a visitor and each role, with a `localhost` flag for the secure context and a `refused` flag on the requests answered 501.

## Amendment: writes (decided, 2026-11-16)

Proposed with MVP 4.3's first write routes (the posts' and pages' create, update and delete) and accepted on 2026-11-16, with PHP's `rest_invalid_json` ported, WordPress's REST hooks at their points and route registration mirroring `register_rest_route()`.

- **Two steps.** `hyscribe_rest::answer()` runs a write's checks as PHP runs them (the body's JSON or form, the arguments' schemas, the permission check, then the callback's checks of `prepare_item_for_database()`) and gives either a finished answer, an error included, or a `Plan`: what to write, made only of values the checks produced. `hyscribe-http` writes the plan and calls `hyscribe_rest::written()`, which makes the answer as PHP's `prepare_item_for_response()` does after the insert. `serve()`, for a site without a writer, answers a plan 501.
- **One writer action.** `hyscribe-http`'s `rest/writes.rs` writes the plan with `hyscribe-write`'s ported functions (`wp_insert_post()`, `wp_update_post()`, `wp_unique_post_slug()`, `stick_post()`, `wp_set_object_terms()`, `wp_trash_post()`, `wp_delete_post()`, the meta functions) in one transaction of ADR 0012's writer, as `saves::act()` writes hs-admin's actions: committed when written, rolled back when PHP refuses (`empty_content`, `invalid_date`) or a statement fails. What `hyscribe-write` does not port answers 501 and writes nothing; a database error shows the error page.
- **The answer from the site as written.** After the commit the site is reloaded (`sticky_posts` is an autoloaded option) and the answer read from it, so its `Allow` and `targetHints` are those of the post as it now is, as PHP computes them after the callback.
- **Shadow mode.** Without a writer, a write past its checks answers 403 with `wp_die()`'s JSON and the login screen's read only message, as hs-admin answers an action.
- **501 before writing.** Anything not ported answers 501 before the write: arguments not ported (`meta`, `format`, a template other than none, a featured image that is an attachment), a multipart body, and content whose answer would be 501 (a shortcode or oEmbed PHP caches, after kses as it is stored). A write is never answered 501 after it is committed.
- **Invalid JSON.** A JSON body PHP's `json_decode()` refuses answers PHP's `rest_invalid_json` (400, "Invalid JSON body passed.", with the `json_error_code` and `json_error_message` PHP gives), ported rather than answered 501.
- **Bodies.** The request carries its body and `Content-Type`; `hyscribe-rest` reads JSON for a JSON media type (`wp_is_json_media_type()`), and for a method other than POST a URL-encoded or untyped body, in `get_parameter_order()`'s order: JSON, the form, the query, the URL, the defaults. The JSON goes through `hyscribe-phpser`'s `json_decode()`; the `rest_serve` fuzz target sends bodies of every type and writes each plan it reaches.
- **Oracle.** `reference/rest/golden.sh` sends a list's fourth column as the body (`json` or `form`), and a request flagged `restore` may write: the database is put back from a dump after it, and the dates of the request's own time read `%now%`. The rows each write makes are the write oracle's (`reference/writes/actions-rest.php`).
- **Hooks.** WordPress's REST hooks fire at their points, under their names and with WordPress's arguments: `rest_pre_dispatch`, `rest_pre_insert_{post_type}`, `rest_insert_{post_type}`, `rest_after_insert_{post_type}`, `rest_prepare_{post_type}` and `rest_delete_{post_type}`. Until the extension runtime they are plain internal calls (docs/EXTENSIONS.md); a hook's result still goes through the checks and the plan, so no hook can write past a check.
- **Route registration.** Routes are registered as `register_rest_route()` registers them: a namespace, a route, and for each endpoint its methods, its arguments' schema and its `permission_callback`. A route registered without a `permission_callback` is refused at registration, which is stricter than WordPress's `_doing_it_wrong()` warning; a route open to everyone says so with an explicit callback, as WordPress's `__return_true`.

## Amendment: namespace indexes, oEmbed, batches and widgets (2026-11-17)

Proposed with the routes the admin and editors still met as 501; the namespace indexes' part reverses "The index waits" for them and needs confirmation.

- **Namespace indexes.** `/wp/v2`, `/oembed/1.0`, `/wp-site-health/v1`, `/wp-block-editor/v1` and `/wp-abilities/v1` are served as `get_namespace_index()` serves them: the routes of the namespace its `namespace` argument names, in registration order, each described from `rest-descriptions.json` without its schema, or with it in the `help` context, and an `up` link to the root. Like the root index's `routes`, they list routes HyScribe answers 501; a namespace that is not a string, on which PHP fails, answers 501. Oracle: `reference/rest/namespaces.list`.
- **oEmbed.** `oembed/1.0/embed` serves this site's published posts and pages as `get_oembed_response_data()` and `get_post_embed_html()` give them, in JSON or, as `_oembed_rest_pre_serve_request()` writes it with SimpleXML, XML, sent before the CORS headers, which PHP sends too late for it. `url_to_postid()` is ported for plain permalinks and the `p`, `page_id` and `attachment_id` arguments; a URL it would match against the rewrite rules, an attachment and a post with a featured image answer 501. `oembed/1.0/proxy` checks `edit_posts` and answers this site's own posts without fetching; any other URL, which `WP_oEmbed` would fetch, and an answer PHP cached in a transient answer 501. The embed's random secret comes from `Site::embed_secret()`; the oracle's is masked (`secret`). Oracle: `reference/rest/oembed.list`.
- **Batches.** `batch/v1` follows `serve_batch_request_v1()`: each request's path parsed, matched and checked by its route's arguments first (`parse_path_failed`, `rest_no_route`, `rest_batch_not_allowed` from the exported descriptions, the arguments' errors, both validation modes), then each answered in turn as a `207` of envelopes with its `Allow` header and `_fields`. A request that writes suspends the batch as a `Pending` holding the rest of it; `hyscribe-http` writes it in its own action and calls `written()`, which answers the next request or gives the next write, so a later request reads the site as the earlier ones left it, as in PHP. Every request is answered once on the site as it is before anything is written, and a batch with any request not ported, or whose arguments are not ported, answers 501 before its first write. Oracle: `reference/rest/batch.list`.
- **Sidebars, widgets and widget types.** Read as a block theme answers them: no sidebar is registered, so the inactive sidebar is the only one and every widget is inactive and renders nothing; the widget types are exported (`rest-widget-types.json`). Reading the sidebars or widgets runs `retrieve_widgets()`, in the permission checks and so in the `Allow` header too, which stores a classic theme's sidebars' widgets as inactive; where it would store them, or `WP_Widget::get_settings()` would store a widget's settings, those routes answer 501 for every method. Only the block widget's form and instance are ported; writes answer 501 past their permission checks. Oracle: `reference/rest/widgets.list` over `widgets.sql` (with `widgets.php`, a test salt for the instances' `wp_hash()`) and `widgets-default.list`.
